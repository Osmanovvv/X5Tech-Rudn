# Мини-план бэкенда «РУДН ИИ × X5 Tech» — админка новостей + приём заявок

> Продолжение основного плана (`2026-07-21-rudn-frontend.md`). Поднимает Task 4.5 из «локального
> инструмента» в полноценный веб-бэкенд: клиент подтвердил, что сайт будет жить на **VPS (Node)**,
> нужен **готовый продукт: фронт + бэк + админка** (см. память `backend-vps-decision`).
>
> **Статус: ЧЕРНОВИК НА УТВЕРЖДЕНИЕ. Кода по этому плану ещё нет.** Реализация — только после «го».

**Goal:** Превратить статический лендинг в готовый продукт на одном проекте Next.js:
маркетинговые страницы остаются статикой (визуал заморожен), добавляются веб-админка `/admin`
(вход + CRUD новостей + загрузка обложек) и реальный приём заявок с формы. Всё подготовлено к
**самостоятельному деплою клиента** на VPS: собранная папка + `.env.example` + README.

**Решения (из опроса пользователя 2026-07-24):**
- Архитектура — **dual-mode**: маркетинг рендерится статически (SSG), Node включается только для
  `/admin` и `/api`.
- Объём — **обе фичи**: админка новостей и приём заявок.
- Хранилище — **zero-dependency (файлы)**: клиент деплоит сам, лишних сервисов на VPS ставить не надо.
- Поставка — «мы всё готовим и проверяем, отдаём папку, деплоят сами они».

---

## Инварианты фазы (нарушение = баг)

1. **Визуал заморожен.** Маркетинговые страницы рендерятся тем же деревом компонентов. После
   переключения конфига и на каждом шаге — пиксель-сверка 320/1200 всех секций = **0.000%**
   (харнесс `qa-shots` + `compare`). Ни один макетный пиксель не двигается.
2. **Маркетинг остаётся пререндеренным (SSG)** даже в Node-режиме. Динамические — только `/admin`
   и `/api/**`. `STATIC=1` собирает чистый статический экспорт (запасной путь, если VPS отвалится).
3. **Zero-dependency хранилище.** Данные — в файлах в каталоге `DATA_DIR` (задаётся env). Никаких
   Postgres/Redis для базового деплоя. Новые runtime-зависимости — минимум и с обоснованием
   (аутентификацию и подпись сессии делаем на встроенном `node:crypto` / Web Crypto, без auth-библиотек).
4. **Секреты — только в `.env` клиента.** Пароль админа, session-secret, (опц.) SMTP задаёт клиент.
   В репозиторий не коммитятся. **Claude их не создаёт и не вводит** — мы даём механизм и утилиту
   генерации хэша, значения ставит клиент.
5. **Персональные данные под защитой.** Заявки (ФИО/почта/телефон) доступны только из админки,
   лежат в `DATA_DIR` вне статической раздачи; в README — где хранятся и как бэкапить.
6. **Бюджет фронта не растёт.** Код админки/API — отдельные чанки, в маркетинговый бандл не попадают
   (First Load JS главной ≤ 150KB, как сейчас 129.6).

**Стек:** Next 16 App Router (тот же проект) · Route Handlers `app/api/**/route.ts` + Server Actions ·
сессии — HMAC-подписанная httpOnly-cookie на `node:crypto` · `sharp` (уже есть) для обложек ·
файловое хранилище с атомарной записью (temp-файл + rename) и внутрипроцессной очередью записи.

## Открытые вопросы / дефолты

1. **SMTP-уведомления о заявках** — по умолчанию ВЫКЛ (только сохранение + просмотр в админке).
   Включаем, если клиент даст SMTP-доступы (тогда +1 зависимость `nodemailer`).
2. **Каталог обложек** (`DATA_DIR/uploads` vs `public/img/...`) — уточнить при реализации, чтобы
   загруженные файлы переживали пересборку и корректно раздавались.
3. **Несколько админов vs один** — по умолчанию один аккаунт из env; расширяемо до списка.
4. **Пагинация /news** при > 12 новостей (из основного плана) — реализуется здесь же, когда объём
   вырастет; сейчас не нужна.
